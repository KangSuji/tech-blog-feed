# 기술 블로그 모아보기

여러 회사 기술 블로그의 새 글을 RSS로 모아 한곳에서 보여 주는 웹 서비스입니다.
태그·블로그별로 걸러 보고, 나중에 읽을 글을 저장할 수 있습니다.

**서비스 주소**: https://tech-blog-feed.vercel.app

## 프로젝트 개요

### 만드는 이유

기술 블로그는 회사마다 흩어져 있어서 새 글을 챙겨 보기 어렵습니다. 이 서비스는 로그인 없이 바로 열어서 최신 글을 훑어보고, 관심 있는 글만 원문으로 넘어가 읽는 흐름을 목표로 합니다.

기능 개수보다 **작게 배포하고 실제 사용 데이터와 피드백으로 자주 고치는 과정**을 기록하는 데 중점을 둡니다.

### 첫 배포(MVP) 범위

1. **피드 보기**: 최신순 글 목록(제목, 블로그, 작성일, 요약), 무한 스크롤
2. **걸러 보기**: 태그·블로그 필터, 키워드 검색
3. **저장하기**: 북마크와 "읽음" 표시(localStorage, 로그인 불필요)
4. **원문 이동**: 클릭 시 원문으로 이동, 클릭 수 집계

본문 전체는 저장하거나 표시하지 않습니다. 제목, 요약, 작성일, 원문 링크만 사용합니다.

### 기술 스택

| 영역           | 선택                             | 이유                                                                            |
| -------------- | -------------------------------- | ------------------------------------------------------------------------------- |
| 프레임워크     | Next.js (App Router), TypeScript | 서버 컴포넌트와 미리 생성한 페이지로 첫 화면을 빠르게 보여 주고 검색엔진에 노출 |
| 스타일         | Tailwind CSS                     | 별도 CSS 파일 없이 빠르게 화면을 만들고 고치기 위해                             |
| 서버 상태      | TanStack Query                   | 무한 스크롤, 검색 결과 캐싱                                                     |
| 화면 상태      | URL 쿼리 파라미터                | 필터·검색 결과를 링크로 공유할 수 있도록                                        |
| DB             | Supabase (PostgreSQL)            | 백엔드 서버를 직접 만들지 않고 DB·권한 관리를 맡기기 위해                       |
| RSS 파싱       | rss-parser                       | RSS 2.0과 Atom을 같은 형태로 읽기 위해                                          |
| 배포·예약 작업 | Vercel, Vercel Cron              | 1시간마다 피드 수집                                                             |
| 분석           | PostHog, Vercel Speed Insights   | 사용 이벤트와 성능 지표(LCP, INP) 측정                                          |

### 구조

```
기술 블로그 RSS ──▶ 수집 작업 (Vercel Cron, 1시간마다) ──▶ Supabase DB
                                                               │ 글 조회
PostHog 분석 ◀── 브라우저 (TanStack Query) ◀── Next.js 서버 (미리 생성한 페이지, Route Handler)
```

#### 블로그 선정과 피드 확인

- 회사 기술 블로그 12곳(수집 대상 9곳)의 피드 주소를 찾고, 각 피드에 제목·링크·작성일·요약이 있는지 직접 확인했습니다.
- 확인하면서 발견한 점:
  - 우아한형제들, 무신사, 잡코리아 등 여러 곳이 `content:encoded`에 **본문 전체**를 담아 보냅니다. → 본문은 저장하지 않고 요약만 저장하기로 했습니다.
  - 잡코리아, 백팩커스(Medium), 무신사 피드에는 요약(`description`)이 없고 본문만 있습니다. → 본문 앞 150자만 잘라 요약으로 씁니다.
  - 카카오페이 피드는 주소는 열리지만 글 항목이 하나도 없습니다. 블로그를 Gatsby에서 Astro로 옮긴 뒤 피드가 비어 있는 것으로 보입니다. → 제외했습니다.
  - 리디와 삼쩜삼은 블로그 전체 피드에 PR 기사나 세금·생활 정보가 섞여 있습니다. → 기술 카테고리·태그 전용 피드 주소로 바꿨습니다.
  - 오늘의집 기술 블로그는 RSS 피드가 없어서 제외했습니다.

#### 프로젝트 생성

- Next.js 16, React 19, Tailwind CSS v4로 생성했습니다.
- 앱 코드는 `src/` 아래에 두어 루트의 설정 파일과 분리했습니다.

#### DB 설계 (Supabase)

- 테이블 정의와 초기 블로그 목록은 SQL 파일로 저장소에 남겼습니다. → [supabase/schema.sql](supabase/schema.sql), [supabase/seed.sql](supabase/seed.sql)
- `posts.link`에 unique 제약을 걸어 **같은 글이 두 번 저장되지 않는 것을 DB가 보장**합니다.
- 두 테이블 모두 RLS를 켜고 **읽기 정책만** 두었습니다. 브라우저(공개 키)에서는 읽기만 가능하고, 쓰기는 서버의 수집 코드(secret key)만 할 수 있습니다.

#### 수집 코드

`GET /api/collect`를 호출하면 등록된 블로그의 피드를 모두 읽어 새 글만 `posts`에 저장하고, 블로그별 수집 결과를 `blogs`에 기록한 뒤 JSON으로도 돌려줍니다. `CRON_SECRET` 인증을 통과한 요청만 실행됩니다.

| 파일                                                         | 역할                                                  |
| ------------------------------------------------------------ | ----------------------------------------------------- |
| [src/app/api/collect/route.ts](src/app/api/collect/route.ts) | 수집 실행: 블로그 조회 → 피드 읽기 → 저장 → 결과 응답 |
| [src/lib/feeds.ts](src/lib/feeds.ts)                         | 피드 글 하나를 `posts` 행 하나로 바꾸는 변환 함수     |
| [src/lib/supabase/admin.ts](src/lib/supabase/admin.ts)       | secret key로 만든 Supabase 클라이언트 (서버 전용)     |

선택 이유:

- **Route Handler**: 수집은 Vercel Cron이 HTTP URL을 호출하는 방식으로 실행합니다. Server Action은 화면의 폼·버튼에서 호출하는 용도라서 외부 스케줄러가 부를 수 없습니다.
- **`Promise.allSettled`**: 피드들은 서로 독립적이라, 한 곳이 실패해도 나머지는 저장되어야 합니다. `Promise.all`은 하나만 실패해도 전체가 실패합니다.
- **`upsert` + `ignoreDuplicates`**: 이미 있는 링크는 덮어쓰지 않고 건너뜁니다(`on conflict (link) do nothing`). 새로 들어간 행만 돌려받아 블로그별 새 글 수를 셉니다.
- **`server-only`**: secret key는 RLS를 무시하는 관리자 키라서, 클라이언트 코드에서 이 파일을 import하면 빌드가 실패하게 막았습니다.
- **수집 결과를 `blogs`에 기록**: 배포 후에는 Cron이 호출하므로 응답 JSON을 볼 사람이 없습니다. 그래서 블로그마다 결과를 DB에 남겨, Supabase 화면에서 어느 피드가 언제부터 실패 중인지 볼 수 있게 했습니다.
  - 성공: `last_fetched_at`을 지금 시각으로 갱신하고 `last_error`를 비웁니다.
  - 실패: `last_error`만 기록하고 `last_fetched_at`은 그대로 둡니다. `last_fetched_at`을 **마지막으로 성공한 시각**으로 정해서, 실패가 이어져도 언제까지 정상이었는지 남게 했습니다.
  - 매 회차 모든 블로그를 다시 읽으므로, 실패한 피드는 별도 재시도 로직 없이 다음 회차에 다시 시도됩니다.
- **`CRON_SECRET` 인증**: 배포하면 수집 URL은 누구나 호출할 수 있습니다. 반복 호출되면 블로그들에 요청이 몰려 봇으로 차단될 수 있어서, `Authorization: Bearer <CRON_SECRET>` 헤더가 맞을 때만 실행하고 아니면 401을 돌려줍니다. Vercel Cron은 이 헤더를 자동으로 붙입니다.
  - 환경 변수가 없으면 비교 대상이 `"Bearer undefined"`라는 문자열이 되어 누구나 통과할 수 있습니다. 그래서 비밀값이 있는지 먼저 확인하고, 없으면 500을 돌려줍니다.

요약 처리 규칙:

1. `description`에서 만든 요약을 쓰고, 없으면 본문(`content:encoded`)에서 태그를 지운 텍스트를 씁니다.
2. 줄바꿈·연속 공백을 공백 하나로 바꿉니다.
3. 비어 있거나 `…` 한 글자뿐이면 요약 없음(`null`)으로 저장합니다. (뱅크샐러드 82개 글 중 12개가 이 경우였습니다.)
4. 150자를 넘으면 잘라서 `…`를 붙입니다.

결과:

- 9곳에서 글 498개를 저장했습니다.
- 같은 수집을 한 번 더 실행하면 모든 블로그의 새 글 수가 0으로 나와, 중복 저장이 막히는 것을 확인했습니다.
- 요약이 `…`인 글 0개, 요약 최대 길이 151자(150자 + `…`)로 요약 규칙이 적용된 것을 확인했습니다.
- 인증 헤더가 없거나 값이 틀리면 401, 맞으면 수집 결과가 나오는 것을 확인했습니다.

수집하면서 발견한 점:

- **리디, 우아한형제들은 403으로 차단됩니다.** 같은 주소를 `curl`로 요청하면 정상이고 Node.js에서 요청할 때만 막힙니다. 두 사이트 모두 Cloudflare가 요청 방식을 보고 봇을 차단하는 것으로 보입니다. 차단을 우회하지 않기로 했습니다. 배포 후 Vercel에서 다시 수집해도 똑같이 403이 나와서 수집 대상에서 제외했습니다. 매시간 막힐 요청을 보내지 않도록 `blogs`에서 삭제하고, 조사 기록은 [docs/blogs.md](docs/blogs.md)에 남겼습니다.
- **뱅크샐러드만 `ERR_INVALID_PROTOCOL` 에러가 났습니다.** 원인은 시드 데이터의 피드 주소 앞에 붙은 탭 문자였습니다. rss-parser는 주소가 `https`로 시작하는지를 보고 요청 방식을 고르는데, 탭 때문에 `http` 방식으로 요청했습니다. DB 값과 seed.sql을 함께 고쳤습니다.

#### 최신순 글 목록 페이지

메인 페이지(`/`)에 최신 글 30개를 제목, 블로그 이름, 작성일, 요약과 함께 보여 줍니다. 제목을 누르면 원문이 새 탭에서 열립니다.

| 파일                                                     | 역할                                              |
| -------------------------------------------------------- | ------------------------------------------------- |
| [src/lib/supabase/public.ts](src/lib/supabase/public.ts) | publishable key로 만든 읽기용 Supabase 클라이언트 |
| [src/lib/posts.ts](src/lib/posts.ts)                     | `getLatestPosts()`: 최신 글 조회와 캐시           |
| [src/app/page.tsx](src/app/page.tsx)                     | 목록을 그리는 서버 컴포넌트                       |

선택 이유:

- **렌더링: 서버 컴포넌트 + `"use cache"` + `cacheLife("hours")` (ISR)**: 글은 수집 주기인 1시간마다만 바뀝니다. 그래서 조회 결과를 1시간 캐시해 요청마다 DB를 거치지 않게 했습니다. 또 서버에서 완성된 HTML을 보내 검색엔진이 바로 읽을 수 있게 했습니다. 빌드 결과에서 `/`가 `○ (Static)`, `Revalidate 1h`로 표시되어 의도대로 적용된 것을 확인했습니다.
- **캐시는 페이지가 아니라 데이터 함수에**: 이 프로젝트는 Next.js 16의 `cacheComponents`를 켜 두어서 예전 방식인 `export const revalidate` 대신 `"use cache"`로 캐시합니다. 2주차에 필터를 URL 쿼리로 받으면 페이지는 요청마다 달라집니다. 데이터 함수에 캐시를 걸어 두면 그때 인자만 추가하면 되고, 인자가 캐시 키에 자동으로 포함됩니다.
- **조회 실패 시 빈 배열 대신 에러를 던짐**: 캐시 함수가 실패를 빈 배열로 돌려주면, 그 빈 결과가 정상 값으로 1시간 동안 캐시됩니다.
- **읽기용 클라이언트를 따로 둠**: 화면은 읽기만 하면 되므로 RLS를 무시하는 secret key 대신 publishable key를 씁니다(최소 권한). 이렇게 해야 RLS 읽기 정책이 실제로 적용됩니다. 로그인 기능이 없어서 쿠키 세션용 `@supabase/ssr` 대신 기본 `@supabase/supabase-js`를 썼습니다.
- **`overrideTypes<Post[]>()`로 결과 타입 지정**: DB 타입을 생성하지 않아서 TypeScript는 조인한 `blogs(name)`을 배열로 추론합니다. 하지만 글 하나에 블로그는 하나라서 실제로는 객체가 옵니다. 실제 응답에서 객체인 것을 확인한 뒤, `as` 대신 Supabase가 제공하는 메서드로 타입을 지정했습니다. 쿼리가 늘어나면 DB 타입 자동 생성(`supabase gen types`)을 검토할 예정입니다.
- **작성일은 `Asia/Seoul` 기준으로 표시**: Vercel 서버는 UTC로 동작해서, 시간대를 지정하지 않으면 한국 시간 새벽에 쓴 글이 전날 날짜로 보입니다.

#### Vercel 첫 배포

- GitHub 저장소를 연결해 `main` 브랜치를 Production으로 배포합니다.
- 환경 변수 4개(Supabase 3개, `CRON_SECRET`)를 등록했습니다. `CRON_SECRET`은 로컬과 다른 운영용 값을 새로 만들었습니다.
- 메인 페이지는 **빌드할 때 Supabase를 조회해 미리 만들어지므로**, 환경 변수는 첫 빌드 전에 등록해야 합니다.

배포하면서 발견한 점:

- **배포 주소로 수집 API를 호출하자 "Protected by Vercel Authentication"이 나왔습니다.** Vercel은 기본 설정으로 Production 도메인을 뺀 배포 주소(배포마다 생기는 고유 주소, 브랜치 미리보기 주소)에 Vercel 로그인을 요구합니다. 브라우저는 Vercel 로그인 쿠키가 있어 열렸지만 `curl`은 막혔습니다. 보호는 끄지 않고 Production 도메인으로 호출해 해결했습니다.
- **배포 환경에서 수집한 결과**: 새 글 82개가 저장되었고, 리디·우아한형제들은 Vercel에서도 403이었습니다. 새 글 중 77개가 뱅크샐러드였는데, 대부분이 이미 저장된 글이었습니다. 아래 개선 로그 1번에 정리했습니다.
